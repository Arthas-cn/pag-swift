# P5 直接 Metal 提交验收（阶段内检查点）

日期：2026-09-28。已在真实macOS窗口完成基础图元的drawable提交，但**P5仍未通过**：本轮没有抗锯齿、整体组alpha、公开PAGSurface/PAGPlayer或三宿主验收。

这是基础提交时的历史检查点。后续整体alpha、80字节常量与局部附件池已经接入，当前进展见[整体透明度验收](P5整体透明度验收.md)；下文保留当时验证范围与测试数量。

## 已接通的路径

`PlaybackFrameRequest → FramePlanner → MetalFramePreparation → MetalFrameBatch → CAMetalDrawable.texture → commandBuffer.present/commit → GPU完成 → PlaybackSubmission`。

- `Rendering/MetalDrawValues.swift`：16字节顶点、64字节常量和真实矩形逆变换裁剪。Double先补回RenderMesh.origin并归一化到NDC，再转Float；拒绝非有限转换。坐标布局、裁剪方向和预乘另有纯值测试。
- `Rendering/MetalShaders.swift`：后台首次编译两条基础MSL管线，后续复用。纯色与RGBA图片均使用预乘SrcOver，单采样BGRA8目标，当前裁剪是硬边。
- `Rendering/MetalResources.swift`：不可变顶点和静图输入上传、有界双向LRU、独立单帧去重保活。跨帧缓存即使禁用，同帧同一来源也共享已经上传的资源，不能重复上传后只计费一次。默认GPU输入留存与单帧预算分别为64MiB，另有已验收CPU几何缓存。
- `Rendering/MetalFramePreparation.swift`：纯色、静图、复合形状和文字fill/stroke按FramePlan顺序转为完整GPU批次；尚未实现的整体alpha明确抛`unsupportedFeature("renderGroupOpacity")`，不逐子图元乘组alpha。
- `Rendering/MetalFrameBatch.swift::encode`：只接收当前CAMetalDrawable，把`drawable.texture`直接设为颜色附件，clear透明并store，然后编码所有基础图元。没有创建整帧中间纹理、resolve尾段、blit或画面像素读回。
- `Rendering/RenderOwner.swift::submit`：真实实现PlaybackSubmitting。在后台专用串行executor求值、上传、编码；在取得显示租约前完成昂贵准备。一个活动提交覆盖后台求值和GPU等待，防止actor可重入创建第二份无界工作。

`PlaybackController.updateTarget`现在可以接收mailbox的实际epoch，状态不变但epoch变化也撤销旧工作；未提供epoch的调度测试保留原先自动生成身份的用法。表面门面尚未实现，不能把此内部入口写成已存在的公开API。

## 平台证据与色彩选择

Apple文档说明普通`makeCommandBuffer()`强持有编码使用的buffer、纹理和管线，直到GPU结束；本实现使用该入口，缓存淘汰不会让当前GPU访问悬空。见[makeCommandBuffer](https://developer.apple.com/documentation/metal/mtlcommandqueue/makecommandbuffer())。

混合使用`one`与`oneMinusSourceAlpha`，RGB和alpha均采用add；这对应预乘输入的SrcOver，不应再次使用sourceAlpha乘已经预乘的颜色。见[Graphics Rendering: Render Command Encoder](https://developer.apple.com/library/archive/documentation/Miscellaneous/Conceptual/MetalProgrammingGuide/Render-Ctx/Render-Ctx.html)。

初版沿已经解码的sRGB数值域，RGBA8输入和BGRA8目标使用unorm；CAMetalLayer声明sRGB。纯色/文字在相同数值域只预乘一次，图片四通道共同乘图层opacity。本轮没有声称上游所有颜色管理选项或真实屏幕像素已经逐项比对。

CPU/GPU共同访问的输入采用Metal设备默认存储模式，不写死Apple GPU的shared纹理条件。Apple当前文档说明默认模式依设备而定，非Apple GPU不支持shared纹理。见[Setting resource storage modes](https://developer.apple.com/documentation/metal/setting-resource-storage-modes)。初始化只用`makeBuffer(bytes:)`和纹理`replace`写入，之后不改写输入资源，不增加最终画面CPU同步读回。

## 提交和清理竞态

最终提交的锁序为PlaybackSubmissionGate → DisplayTargetMailbox绘制许可；双锁内只验证完整身份并执行已编码buffer的present/commit。求值、取drawable、编码和等待GPU均在锁外。显示beginMutation、关闭或播放撤销能阻止尚未入队的旧帧。

真实Metal API Validation测试曾在“编码完成后、commit之前撤销显示”的路径报重复恢复continuation。错误代码假设未提交buffer不会再有完成回调；现已移除此假设，新增`MetalSubmissionCompletion`：

1. 系统GPU结果、owner确认commit结束、提交前放弃共享一个锁保护状态。
2. GPU结果先到只暂存，直到owner离开双锁和受控drawable借用作用域才允许清理；不依赖回调必定异步到另一条线程。
3. 未提交的放弃可以取走唯一continuation；迟到/重复回调不能再次释放租约或覆盖结果。
4. 确认提交之后，主动取消不能提前释放租约，必须等真实GPU结束。播放层显式等待者的及时取消仍由P4负责。

纯值测试覆盖取消先到、GPU先到、提前回调、重复回调和旧清理不能释放新租约。真实窗口回归再次覆盖编码后撤销，没有用测试替身代替实际Metal完成。
