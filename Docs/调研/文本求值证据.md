# P3 文本求值证据与实施入口

2026-09-28。本记录是已读取源码事实和实施边界。libpag 根与提交同 [求值证据](求值证据.md)；纯值排版、CoreText 真实字体/轮廓资源及文本 FramePlan 已接入，完整 TEXT04 已通过计划与数值测试。颜色字形、非轮廓字体、非空背景仍具体 unsupported，GPU 显示尚未验收。

## 已核对的上游链路

`TextContentCache::initTextGlyphs` → `TextRenderer::GetLines` → `BuildGlyphs` → `Glyph::BuildFromText` → `TextShaper::Shape`。非 HarfBuzz、非 FreeType 的平台路径先调用 `Platform::shapeText`；Cocoa 的 `platform/cocoa/private/NativeTextShaper.mm` 使用 CoreText，失败才可能落到 Primitive。不要把新 `src/renderer/TextShaper` 或 PAGX 的布局规则混入这里的经典 PAG TextSource。

`NativeTextShaper::Shape` 建立 UTF-16 下标到原 UTF-8 起点的映射（非 BMP 字符占两个 UTF-16 单元），从 CTLine 各 CTRun 读取实际字体、glyph ID、string index 与 position。颜色字体中连续同 x 位置的 glyph ID 归为一组。该函数没有把 CTLine 的排版位置整体交给 PAG 布局器，不能直接以 CTFrame/System TextKit 排版替代之后的 PAG 算法。

`Glyph::BuildFromText` 保存实际 fallback 字体，以相邻 cluster 索引切出 name；`Glyph` 用首 glyph 的 nominal advance、bounds 和字体 metrics。空 bounds 但正 advance 的 glyph 用 ascent/descent 补逻辑范围，空格单独以 A 的上下边界修正。相邻 cluster 在复杂 RTL/组合字符场景的原算法需要单独验证，不应复制可能的无符号长度下溢。

## 布局的源码事实

来自 `src/rendering/renderers/TextRenderer.cpp`：

| 符号 | 已确认规则 |
| --- | --- |
| `CreateTextLayout` | point text 从 baseline=0 开始。水平框使用 boxTextPos 平移，firstBaseline 减 boxTextPos.y；竖框交换宽高，以右边界和 boxTextPos.y 建坐标映射 |
| `CreateTextLayout` | leading=0 时 lineGap=`roundf(fontSize×1.2)`；tracking=`roundf(tracking×fontSize×0.001)`；baselineShift 保留源单位 |
| `CreateTextLayout` | 用 glyph 中最小 ascent、最大 descent 的比例把 1.2×字号拆为 fontTop/fontBottom；空串或没有有效 metrics 时要先处理，不能让 0/0 进入计划 |
| `CalculateNextLineIndex` | 逐 glyph advance 累加，非首 glyph 加 tracking；显式换行终止当前行。以“下一 glyph 会否超出宽度”决定分行，并非按单词的系统换行 |
| `AdjustToFitBox/CalculateGlyphScale` | 从原字号逐次减1、到不大于5为止，寻找满足原框可用行区域的缩放。调整字形大小、leading/tracking、首基线及纵向居中；负/零行距等极值必须有有界行为，不能无输入忙循环 |
| `CalculateDrawX` | 点文本只对居中/右对齐偏移；框文本区分普通左/中/右和 FullJustify 的末行策略 |
| `CalculateLetterSpacing` | FullJustify 可以按行内 glyph 数分配剩余宽度；一字/空行必须避免除零，末行或显式换行采用对应末行策略 |
| `ApplyLayoutToGlyphInfos` | baseline 超过框底才停止；绘制 y=baseline-baselineShift。空行仍影响逻辑 bounds；没有源码依据把文字框强行作为图层 clip |
| `ApplyMatrixToGlyphs` | 先布局位置，再用方向坐标矩阵映射位置；glyph 保留自己的竖排 extraMatrix 和 glyphScale |

来自 `src/rendering/graphics/Glyph.cpp`：竖排中单字节 name（字母、数字和 ASCII 标点等）旋转90度，并左移 `(capHeight+xHeight)×0.25`；其他字形用字体 vertical offset/advance，垂直 advance 为零时退回水平值。不能用“把整段文字旋转90度”替代这两类字形。

## 颜色、背景和描边

- `TextContentCache::createContent` 将文本背景放在普通文本之前。颜色 glyph 另有保留路径，不能把 emoji 的原色简单当单色 mask。
- `TextRenderer::BuildGlyphs` 把 source fauxBold/fauxItalic、fill/stroke、strokeWidth、strokeOverFill 交给 glyph；本库公开合同规定 fill/stroke 均 nil 为无文字像素，不能照搬旧代码“否则默认 Fill”的分支破坏此约定。
- `TextContentCache::CopyLines` 在 strokeWidth<0.1 时对纯描边跳过，对填充+描边退为填充。
- 已核对 `rendering/graphics/Text.cpp::MakeTextRun/draw/drawTextRuns`：初始 paints[0]=fill、paints[1]=stroke，strokeOverFill=false 或 fill 不存在时交换。绘制先遍历全部 run 的第一份 paint，再遍历全部 run 的第二份 paint；不能改成逐 glyph 交替描边/填充。run 按 styleKey 首次出现顺序保留，key 含字形线性变换、颜色/alpha、TextStyle、strokeWidth 和实际 typeface。
- `RenderTextBackground/RenderBackgroundPath` 以行 glyph bounds/advance 建背景，margin=max(fontSize×0.4,strokeWidth)，相邻行间隙按半间距补齐并 round 边界；整体拐角半径最大25且不超过背景较短边的1/3。不能简单把 boxTextSize 整框填色。

## 已验证的 Swift 并发边界

本机 Xcode 27 / Swift 6.4、macOS26 target，临时文件 `/private/tmp/pag-swift-coretext-sendable-probe.swift` 使用普通 `import CoreText/CoreGraphics`，以 `-swift-version 6 -enable-upcoming-feature ApproachableConcurrency -strict-concurrency=complete -warnings-as-errors -typecheck` 验证：`CTFont`、`CTLine`、`CTRun`、`CGPath` 放入 Sendable struct 都被编译器拒绝。此为预期的能力探针失败，库的完整 swift test 仍通过。

Apple 官方 [Core Text Overview](https://developer.apple.com/library/archive/documentation/StringsTextFonts/Conceptual/CoreText_Programming/Overview/Overview.html) 说明函数可在多个线程调用，但不得并发修改共享输入；这不等于 SDK 已提供 Swift Sendable conformance。新实现应在显式 `@concurrent` 准备调用内创建/使用/释放系统字体、line、run、path，把排版结果转换为不可变标量、路径命令或字形输入资源再返回。不添加整库 `@MainActor`，也不靠 `@preconcurrency` 或宽泛 `@unchecked Sendable` 消除诊断。

## 纯值排版实施与严格边界

已新增 internal `TextLayout`、`TextLayoutSettings`、`TextLineBreaking` 与输入/输出值，按本文证据执行 FontSize/leading/tracking、逐 glyph 断行、七种 justification、框自动适应、基线与竖排坐标映射。`TextGlyphMetrics` 必须来自之后的整形准备：advance 与 ascent/descent 已按源方向选择，bounds 已转换到统一横排计算空间。返回输入索引、图层局部位置、逻辑行范围、glyphScale 和 bounds；没有创建字体、字形轮廓、FrameCommand 或像素。

Swift 使用 Float 保持源码运算次序，纯值布局同步调用，预期由后台准备入口执行。测试采用独立指定的 glyph 指标，不能以这些测试声称 TEXT04 的真实字体或画面已经验收。已覆盖七种点/框对齐、显式/自动换行、空输入/空行/末尾换行、负 tracking/点文本负 leading、整数步字号适应、缩字号后不缩 baselineShift、上下居中、竖排框右边缘映射、超宽 glyph 和框外边缘。

本库在下列不安全源边界选择明确行为并已先写入架构：空输入不计算 metrics 的 0/0；单项 FullJustify 无间隙可分配，保留 tracking；非空却没有有效垂直 metrics 报 invalidFile；框尺寸非正或有效 leading 非正报具体 unsupportedFeature；中间 Float 非有限报 invalidFile。输出按最坏一项一行预留 256 字节/输入项的保守逻辑预算，候选字号和每次 glyph 检查/输出另受默认4,194,304次工作量限制。Float 减1不能推进时也报 maximumTextLayoutWork，不循环或近似替代。

核对布局还发现架构初稿的“默认 clip 保持原始表现”与源码不符，已经先修正文档：默认无附加 overflow 覆盖，P8 的显式 clip/marquee 是额外呈现，nil 恢复 PAG 原始布局。P8 公共签名仍待实现，没有更改现有生产 API。

## 真实资源与计划验收

`CoreTextShaper` / `SystemGlyphGeometry` 同步执行于 `PreparedScene.prepare` 的显式 @concurrent 作用域。CTFont/CTLine/CTRun/CGPath 不保存到 Sendable 结果；GlyphOutline 为不可变元素类，文本 PreparedTextLayer 只有值、不可变路径和纯值字体诊断。字体匹配失败保留系统级联结果；glyph0 的缺字索引单独记录。缓存按实际字体相等性和 glyph ID，避免把相同文本片段误当作相同上下文 glyph。

cluster 用已验证的 UTF-16 标量边界映射，RTL/重复索引按逻辑右邻起点决定范围，避免上游相邻无符号长度相减的下溢。保持 CTLine 的视觉 glyph 顺序与源 PAG nominal advance 布局，没有擅自引入 CTLine 的 kerning/基线偏移；复杂组合字形的逐像素结果仍待显示阶段核对。

`PreparedScene` 只有在同一 DocumentStorage 且完整 PAGText 相等时复用文字资源；其余不公开编辑的 SourceText 字段由同一存储保证不变。编辑产生新 TextResourceID UUID，保留旧帧引用，不覆盖旧资源。FramePlanner 不调用 CoreText 或创建路径，只保活 PreparedTextLayer 并发出各 pass；多源实例共享资源但保留各自矩阵/ID。整体图层 alpha 包住全部 pass，默认没有文字框 clip。

完整 `editing/TEXT04.pag` 验证：9个实际字形、PingFangSC-Medium、1行、glyphScale=1、先 stroke 后 fill。独立读取源 TextSource 得 firstBaseline=−5.528076171875、boxPosition=(−93.75,−23)、boxSize=(187.5,20.75)；当前系统字体 nominal 总宽179.328，居中后首/末 glyph 的 x=−89.664/65.664，全部 y=−5.528076171875。测试使用水平0.002、基线0.0001容差；字体版本或最低系统实际差异需后续记录，而非宣称跨系统字节一致。独立中文字形“中”的 CG 后端逻辑 bounds=(1,−21,23,4)、advance=24、vertical offset=(−12,20.64) 有固定数值测试。

最新完整库验证：`swift test` **236 tests / 32 suites passed**，日志 `/tmp/pag-swift-p3-text-final.log`。全部67个库源文件另外用 `swiftc -c -whole-module-optimization -swift-version 6 -strict-concurrency=complete -warnings-as-errors -enable-upcoming-feature ApproachableConcurrency -target arm64-apple-ios26.0` 与 iPhoneOS27 SDK 编译成功，日志 `/private/tmp/pag-swift-p3-ios-compile/build.log`；没有运行 xcodebuild 或安装宿主。iOS 仅编译证据，运行/实际字体/三宿主结果仍待 P6。
