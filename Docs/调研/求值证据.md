## 已核对并实现：场景时间与控制父链

- `LayerRenderer.cpp::DrawLayer` 以 `layerFrame - layer.startTime` 得到 contentFrame；`LayerCache.cpp::contentVisible` 要求 0 ≤ contentFrame < duration，再检查变换可见性。
- `FrameCache.h::getCache` 将内容帧钳到层合法帧，再加 startTime 调用具体变换/内容求值。因此父链变换由子层请求的同一 layerFrame 采样，不能把 parent opacity 或 visible 简单当成场景树继承。
- `base/PreComposeLayer.cpp::getCompositionFrame` 使用 `roundf(Float(layerFrame - compositionStartTime) × childFPS / parentFPS)`。`PreComposeContentCache.cpp` 的源缓存路径使用该方法，`CompositionCache.cpp` 将子内容帧钳到合成首末帧。
- `rendering/layers/PAGComposition.cpp::gotoTime` 的可编辑层路径使用微秒：compositionOffset = compositionStartTime - source.startTime + instance.startFrame；偏移转微秒特意取 floor 后，再把 layerTime - offsetTime 传给子层。其源码注释明确给出 30fps、100000µs、offset=1 时用 ceil 会落到前一帧的问题。
- 同文件中 `PAGComposition::draw` 根据 contentModified/contentStatic 选择源缓存或可编辑子层路径；`PAGLayer::gotoTime` 按自己的 frameRateInternal 取 floor。`PAGLayer::frameRateInternal` 对导入文件返回 file->frameRate；`PAGComposition` 导入构造的 `_frameRate` 也取文件帧率。`updateDurationAndFrameRate` 用于 `emptyComposition` 的子项增删，不是导入文件各个源合成的统一帧率转换；`PAGFile::BuildPAGLayer` 直接逆序构造源子层，Codec 未归一化矢量 fps。

架构第 5.1 节已明确选择：统一根 floor 帧，再用 `getCompositionFrame` 的 Float 比值/roundf 源帧映射和子合成首末钳制；不随编辑/缓存切换时钟。这是本库的合同选择，不宣称完全复刻上游两条路径的差异。对本地 119 份 PAG 的只读清点，112 份包含 vector composition，未发现单份文件内不同 vector fps；不能由此推导格式限制。混合帧率暂用源码公式语义图测试，仍缺真实混合 fps 导出文件的显示对照。

Swift `SceneTiming` 覆盖根请求/代表帧时间、负起点、右开可见区间、媒体内容微秒、独立 compositionStart、30→60/15 fps、half-away 舍入、子首末保持、数值溢出。`CompositionTopology` 在验证时保存父下标；`LayerTransformSampler` 在一次调用内按需缓存父累计矩阵，支持 2,000 层深链与并行随机采样；不依赖父层 active、opacity 或自身可见区间。此缓存不跨帧、实例或任务共享可变状态。

| `ShapeContentCache::createContent`（另文件） | 按属性时刻生成形状内容，静态内容可复用 | 当前源形状均为常量：`PreparedScene.prepare` 后台准备一次，多个帧/实例/同源编辑共享几何；动画形状仍由解码入口明确拒绝 |

矩形后端的额外证据：当前官方 [TGFX Path::addRoundRect](https://github.com/Tencent/tgfx/blob/main/src/core/Path.cpp) 将矩形和半径交给 SkRRect，再保留绕序加入路径；官方 [SkRRect::initializeRect/setRectXY](https://github.com/google/skia/blob/main/src/core/SkRRect.cpp) 规范矩形边界，非正半径为直角、零面积为空。这些只用于后端几何规则，**不是 PAG 字节布局证据**。读取日期 2026-09-28。本地 DEPS 记录 TGFX `062b864b1425de23fe5a63fbb67137974a4af215`，对应依赖源码本地未展开，固定提交网页未能取得；此处明确引用当前官方实现，不声称完成了该固定版本的负尺寸显示对照。P5 仍需真实显示验证。

`RoundedRectangleContour` 保存解析圆弧与累计仿射矩阵，未偷换成四段近似三次曲线或栅格图；实际网格/抗锯齿在 P5。所有轮廓属于一次 nonzero 填充资源，形状图层自身 alpha 和子组 alpha 用无额外裁剪的组指令保留。Geometry ID 由文档身份、源层下标和几何序号组成，多次预合成实例不重复生成几何。

`PreparedScene.prepare` 与 `FramePlanner.prepare` 均显式 `@concurrent`。前者以独立默认 64 MiB 预算编译静态资源，后者只生成当前命令与保活表；准备/逐帧均检查取消，不发布部分结果。显式 reusing 只接受同一个 DocumentStorage，使用新编辑快照但共享静态形状；降低预算仍会核对原准备成本。没有进程全局无界几何缓存，也没有每帧重建 CGPath 或复制轮廓。组完全透明时只累计向外提供的路径，不为它自己的 paint 建资源。

`ShapePreparationTests` 和 `ShapeFramePlanTests` 已验证上述规则。完整真实 `red.pag` 现可进入形状 FramePlan：局部矩形 1500×300、中心经组与层映射到 `(360,640)`，左上角约 `(0.141941607,1.723804474)`；360×360 逻辑尺寸、2倍 aspectFit 的中心是 `(360,360)`。不同时间和重复实例持有同一个 ShapeGeometry 对象。测试只证明几何和计划，尚未证明实际 GPU 填充的孔洞、圆角边缘或颜色。

## 下一项证据入口

普通轮廓静态文本的布局/字形资源已接入 FramePlan，证据、源码固定提交及具体限制见 [文本求值证据](文本求值证据.md)。[P3验收](P3验收.md) 已通过，下一阶段是 P4 内部播放状态机。颜色字形、非轮廓字体和文本背景仍是 P7 的明确实现目标，不能把当前 unsupported 当成最终完成。
