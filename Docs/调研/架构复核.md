## 3. 发现并已解决的问题

| 严重度 | 初稿问题 | 为什么必须修改 | 最小修订与位置 |

| 高 | 独立 CALayer 显示目标没有显式活动状态，却假设 nextDrawable 可以判断是否挂窗口；零尺寸也无法用正 PAGSize 表达。 | 可能在隐藏目标继续推进/绘制，或由实现者猜测生命周期。 | 第 6.1 节增加 `setPresentationActive`，默认 false；零布局先 inactive，保留最后合法尺寸，恢复后重新激活。 |

| 高 | 预合成复用时图层 ID、可见性及展开预算未固定。 | 同一源记录的多个实例会互相污染；无环 DAG 仍可能指数展开。 | 第 3.3 节采用文档身份加实例路径；可见性按实例修改，索引/名称替换命中关联实例；源记录数与展开实例数同时受上限约束，分配前饱和计数。 |

## 4. 独立编译证据

工具链为 Apple Swift 6.4，`swiftlang-6.4.0.34.1`，Xcode 27 SDK；主机为 arm64 macOS 27。使用的主要参数为：

```text
-c -swift-version 6 -strict-concurrency=complete
-enable-upcoming-feature ApproachableConcurrency
-target arm64-apple-macosx26.0
```

iOS 探针另指定已安装的 iPhoneOS 27 SDK 与 `-target arm64-apple-ios26.0`。没有运行 xcodebuild、选择设备或启动模拟器。

| 探针 | 结果 | 结论的范围 |
| --- | --- | --- |
| 从最终架构文档提取全部公开 Swift 声明，补最小方法体、条件编译及系统继承要求 | 两个平台 `swiftc -c` 均通过 | 类型引用、隔离标记、async/throws、Sendable 公开面可表达；不证明方法行为。 |
| RenderWorker actor 内部持有 Metal device/queue/command buffer；完成回调仅提取可发送的结果回传 | 两个平台 `swiftc -c` 均通过 | GPU 所有者与值型完成通知的隔离方向可行。 |
| `@concurrent` 解码函数输入/输出均为 Sendable 值 | 两个平台 `swiftc -c` 均通过 | 可显式离开调用 actor 执行 CPU 工作。 |
| 对 CVPixelBuffer、CMSampleBuffer 要求 Sendable | 编译按预期拒绝 | 两种对象不能因 SDK 来自系统就假定可发送。 |
| 回调直接 `Task { await owner.receive(pixelBuffer) }`，receive 使用 sending 参数 | `-typecheck` 未报错，但 `-c` 按预期拒绝并报告 region isolation 风险 | 只做 typecheck 可能遗漏关键并发诊断；sending 不能自动消除回调的别名。 |
| 帧缓冲留在局部锁保护信箱，Task 只发送 frame ID，唯一所有者同步取出 | 两个平台 `swiftc -c` 均通过 | 可实现受同步的局部资源桥；仍必须验证容量、取消、只消费一次及 GPU 保留生命周期。 |

这些探针放在 `/tmp`，没有作为库实现或测试替代物。最小方法体只用于让声明完成编译，未调用；不能把编译成功写成完成播放功能。

## 5. 后续阶段必须验证的范围

这些是合同已经规定的实现验收项，不是当前架构门禁遗留问题。到达相应阶段时，未通过就不能继续宣称该阶段完成。

- **P1a–P3：格式与求值。** 每项字节解释核对上游完整读取路径；实际简单文件的支持闭包必须通过真实夹具证明。不能凭 red 等名字推断只有纯色层；拒绝未知语义而非透明降级。
- **P5：显示桥。** CAMetalLayer 受控挂卸载与后台渲染属性的访问需要 Apple 行为证据和生命周期测试。不得让主线程等待 nextDrawable、持锁等待 GPU 或同步排空。动态 resize、detach、旧 completion 与资源释放均需验证。
- **P5/P6：实际呈现。** 编译探针没有证明任何像素已正确显示。必须检验实际 drawable 附件、三宿主一致性、零尺寸/隐藏/恢复与末帧呈现，不增加公开读回 API 来绕过验收。
- **P7：内嵌视频。** VideoToolbox 输入、NAL/config、重排序、PAG alpha 与色彩转换，及资源桥保留到 GPU 完成，都需要真实 PAG 样例验收。
- **P8：外部视频与动图。** AVPlayerItemVideoOutput 的局部时间、精确 seek、末帧保持和静音须实测。GIF/WebP 必须验证逐帧内容、时序、合成/处置及循环；当前 macOS 27 的有限 ImageIO 探针不代表最低 iOS/macOS 26 已验证。
- **P9：性能。** 后台隔离、有界排队/内存和直接绘制的设计不能替代测量；需记录具体样例/设备上的时延、分配、长时间循环与替换表现。

## 6. 实现优先事项

1. 按通过后的 P0 合同建立基础值、错误和确定性时间/缩放规则，完整运行包验证；不提前落地 loader/player 占位 API。
2. 从 P1a 维护字节证据与支持矩阵，P1b 只选择可完整覆盖的真实文件，P1c 再交付完整载入/缓存生命周期。
3. P5 优先通过最小显示桥门禁，再接入真实帧；P7/P8 复用经过审计的资源所有权方式。

设计已经做得好的部分是：不可变文档与编辑/播放状态分离、微秒与进度清楚区分、三宿主只承担生命周期，以及渲染目标与视图分离但不扩大到离屏导出。主要架构风险集中在后续显示层/视频的系统框架边界和完整 PAG 功能覆盖；文档已经给出显式验收与先修合同再换方案的出口。
